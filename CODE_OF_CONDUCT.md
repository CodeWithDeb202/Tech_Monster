# Code of Conduct

## Tech Monster

Tech Monster is committed to providing a professional, respectful, inclusive,
and collaborative environment for everyone who contributes to the project.

This Code of Conduct applies to all project contributors, maintainers,
reviewers, collaborators, and community participants when they are
participating in Tech Monster project spaces.

This includes, but is not limited to:

- GitHub repositories
- Issues
- Pull requests
- Code reviews
- Discussions
- Project documentation
- Development-related communication
- Community spaces directly associated with the project

The goal of this document is not to restrict healthy technical disagreement.

The goal is to make sure that technical disagreement remains professional,
constructive, and focused on improving the project.

---

## Our Standards

Everyone participating in the project is expected to behave professionally
and respectfully.

Examples of positive behavior include:

- Communicating respectfully.
- Listening to different technical perspectives.
- Giving constructive feedback.
- Accepting reasonable criticism.
- Asking questions when requirements are unclear.
- Explaining technical decisions with evidence and reasoning.
- Helping new contributors understand the project.
- Giving credit to other contributors for their work.
- Respecting different levels of experience.
- Focusing discussions on the problem rather than the person.
- Being patient when reviewing or explaining technical concepts.
- Keeping discussions relevant to the project.
- Protecting private and sensitive information.
- Reporting security vulnerabilities responsibly.
- Taking responsibility for mistakes and correcting them.

A contributor does not need to agree with another contributor to communicate
respectfully with them.

---

# Expected Communication

## Be Respectful

Technical discussions can become intense, especially when architecture,
security, performance, or product decisions are being discussed.

Disagreement is acceptable.

Personal attacks are not.

Prefer:

> "I think this approach could create a database consistency problem because
> the operation can be executed concurrently. Could we handle the operation
> transactionally?"

Avoid:

> "You clearly don't understand databases."

The first statement addresses the implementation.

The second attacks the person.

---

## Criticize Code, Not People

Code review should focus on:

- Correctness
- Security
- Maintainability
- Performance
- Architecture
- Testing
- User experience
- Accessibility
- Documentation

Review comments should not criticize someone's intelligence, experience,
background, personality, or character.

A useful review comment should help the contributor understand:

1. What is wrong.
2. Why it matters.
3. What could be improved.

---

## Assume Good Intent

Not every mistake is intentional.

A contributor may:

- Miss an edge case.
- Misunderstand an existing abstraction.
- Use an unfamiliar pattern.
- Forget to update documentation.
- Make an incorrect assumption.
- Introduce a regression accidentally.

Start with clarification rather than accusation.

---

# Unacceptable Behavior

The following behavior is not acceptable in Tech Monster project spaces.

## Harassment

Harassment includes unwanted or hostile behavior directed toward another
participant.

Examples include:

- Personal insults.
- Repeated unwanted contact.
- Intimidation.
- Threats.
- Deliberate humiliation.
- Persistent personal attacks.
- Targeted hostile behavior.

---

## Discrimination

Discriminatory behavior based on personal characteristics is not acceptable.

Contributors must not use project spaces to demean or exclude someone based on
characteristics unrelated to their technical contribution.

Project decisions should be based on relevant factors such as:

- Technical correctness.
- Security.
- Maintainability.
- Performance.
- Project requirements.
- User impact.
- Contributor responsibilities.

---

## Threats

Threats of violence, harm, retaliation, or other intimidation are prohibited.

---

## Sexual Harassment

Unwelcome sexual comments, sexualized communication, or inappropriate sexual
behavior toward another participant is prohibited.

Project spaces should remain professional and appropriate for software
development collaboration.

---

## Trolling and Deliberate Disruption

The following behavior is discouraged and may result in moderation:

- Deliberately derailing technical discussions.
- Repeatedly posting irrelevant content.
- Intentionally disrupting issue or pull request discussions.
- Repeatedly reopening resolved arguments without new technical information.
- Deliberately creating misleading reports.
- Deliberately submitting harmful or malicious code.

Healthy disagreement is different from deliberate disruption.

---

# Professional Technical Disagreement

Different technical opinions are expected in a software project.

Contributors may disagree about:

- Framework choices.
- Architecture.
- API design.
- Database design.
- Naming.
- State management.
- UI design.
- Performance strategies.
- Testing strategies.
- Dependency choices.
- Deployment approaches.

These disagreements should be handled using technical reasoning.

Useful discussion may include:

- Documentation.
- Benchmarks.
- Test results.
- Security implications.
- Existing project conventions.
- Maintenance costs.
- User requirements.
- Compatibility considerations.

When a discussion cannot be resolved immediately, maintainers may make a final
decision based on the project's requirements and long-term maintainability.

A final maintainer decision should be respected unless new evidence justifies
reconsideration.

---

# Code Review Conduct

Code reviews are an important part of Tech Monster development.

Reviewers should:

- Review the implementation objectively.
- Explain important concerns.
- Distinguish blocking issues from suggestions.
- Avoid unnecessary personal comments.
- Avoid demanding stylistic preferences without a project-level reason.
- Consider existing project conventions.
- Recognize good implementation decisions.
- Ask questions when intent is unclear.
- Avoid unnecessarily hostile or dismissive language.

Contributors receiving reviews should:

- Consider feedback objectively.
- Ask for clarification when necessary.
- Explain decisions respectfully.
- Address valid concerns.
- Avoid taking technical criticism personally.
- Avoid escalating disagreements into personal arguments.

---

# Maintainer Responsibilities

Maintainers are responsible for helping maintain a healthy project environment.

Maintainers should:

- Apply this Code of Conduct consistently.
- Encourage respectful technical discussion.
- Address serious misconduct appropriately.
- Protect sensitive information.
- Avoid favoritism in technical decisions.
- Keep project decisions focused on project goals.
- Explain significant decisions where practical.
- Treat contributors fairly.

Maintainers should not use their position to intimidate contributors or
silence reasonable technical criticism.

---

# Security and Responsible Disclosure

Security issues should not be publicly disclosed before maintainers have had
an opportunity to investigate them when public disclosure could put users or
systems at risk.

Do not post sensitive security information in:

- Public GitHub issues.
- Public pull requests.
- Public discussions.
- Public comments.

Sensitive information may include:

- API keys.
- Passwords.
- Authentication tokens.
- Private keys.
- Database credentials.
- Session secrets.
- Personally identifiable information.
- Exploitable vulnerability details.

If a security issue is discovered, follow the project's designated security
reporting process.

If the repository provides a `SECURITY.md` file or GitHub private security
advisory mechanism, use that process instead of publicly exposing the
vulnerability.

Never test an alleged vulnerability against systems that you do not own or
have explicit permission to test.

---

# Privacy

Contributors must respect the privacy of other participants.

Do not publish or expose another person's private information without their
permission.

This includes:

- Personal contact information.
- Private conversations.
- Authentication information.
- Private repository information.
- Private credentials.
- Personal documents.
- Sensitive screenshots.
- Private account information.

Only share information that is necessary for legitimate project work.

---

# Intellectual Property and Attribution

Contributors should respect the intellectual property of others.

Do not submit code, documentation, images, designs, or other assets that you do
not have the right to distribute.

When using third-party material:

- Verify the license.
- Follow the license requirements.
- Provide attribution when required.
- Keep required copyright notices.
- Do not remove license information.
- Do not represent someone else's work as your own.

If you are unsure whether an asset can legally be used, do not add it until the
licensing situation has been clarified.

---

# Contribution Quality

Professional conduct also includes responsible software development.

Contributors should make reasonable efforts to ensure that contributions do
not intentionally introduce:

- Malware.
- Credential theft.
- Unauthorized access.
- Backdoors.
- Deliberate data destruction.
- Malicious tracking.
- Deliberate security vulnerabilities.
- Unauthorized external system access.

Security-sensitive functionality should be reviewed carefully before merging.

---

# Reporting Problems

If you experience or observe behavior that violates this Code of Conduct,
report it to the project maintainers through an appropriate private channel.

Do not create a public issue containing sensitive personal information about
another contributor.

When reporting a serious incident, provide as much useful information as you
can safely provide.

Useful information may include:

- What happened.
- When it happened.
- Where it happened.
- Who was involved.
- Relevant GitHub issue or pull request.
- Screenshots or logs when appropriate.
- Whether the behavior is ongoing.
- Any immediate safety or security concerns.

Do not include unnecessary personal information.

---

# Handling Reports

Maintainers should review reports seriously and as confidentially as
practical.

Depending on the situation, maintainers may:

- Ask for additional information.
- Review relevant project history.
- Speak privately with involved participants.
- Request that inappropriate content be removed.
- Close or moderate discussions.
- Ask a participant to stop specific behavior.
- Restrict project participation.
- Remove inappropriate contributions.
- Temporarily or permanently restrict access to project spaces.

Actions should be proportional to the situation.

Serious incidents may result in immediate action.

---

# Confidentiality

Information shared privately during a conduct or security report should not be
publicly disclosed unless disclosure is necessary, legally required, or
authorized by the appropriate parties.

Maintainers should avoid discussing private reports publicly.

---

# False or Malicious Reports

Reports made in good faith are protected.

A contributor should not be punished simply because an investigation does not
confirm the reported behavior.

However, intentionally fabricated reports made to harass, intimidate, or harm
another participant are themselves inappropriate and may be addressed as a
Code of Conduct violation.

---

# Retaliation

Retaliation against someone who:

- Reports misconduct.
- Participates in an investigation.
- Provides evidence.
- Requests clarification.
- Raises a legitimate security concern.

is not acceptable.

Contributors should be able to raise legitimate concerns without fear of
personal retaliation.

---

# Scope

This Code of Conduct applies to behavior that occurs within Tech Monster
project spaces.

It may also apply to behavior outside project spaces when that behavior has a
direct and significant impact on the project's ability to maintain a safe and
professional collaboration environment.

Examples may include:

- Coordinated harassment of project participants.
- Threats related to project participation.
- Deliberate disclosure of private project information.
- Retaliation connected to project reporting.

---

# Conflict Resolution

When a disagreement is minor and does not involve misconduct, contributors
should attempt to resolve it through constructive technical discussion.

A recommended process is:

1. Identify the disagreement.
2. Clarify assumptions.
3. Explain technical reasoning.
4. Review evidence.
5. Consider alternative approaches.
6. Look for a project-aligned solution.
7. Ask a maintainer to decide if necessary.

The goal is resolution, not winning an argument.

---

# Maintaining a Healthy Project

A healthy open-source project requires participation from everyone.

Contributors can help by:

- Welcoming new developers.
- Writing clear issues.
- Giving useful code reviews.
- Improving documentation.
- Reporting bugs responsibly.
- Sharing technical knowledge.
- Avoiding unnecessary hostility.
- Respecting project decisions.
- Helping maintain project quality.

Small positive interactions make collaboration easier for everyone.

---

# A Note to New Contributors

You do not need to know the entire codebase before contributing.

It is completely acceptable to ask questions.

If you do not understand something:

- Ask for clarification.
- Explain what you already investigated.
- Include relevant error messages.
- Link to the code you are referring to.
- Be specific about what is unclear.

A question such as:

> "I traced this request from the frontend component to the controller, but I
> don't understand why authorization is checked in this middleware instead of
> the service. Is there an architectural reason for this?"

is a good contribution to the project.

---

# Maintainer Decision Making

When maintainers need to make a final technical decision, they should
prioritize:

1. Security.
2. Correctness.
3. User impact.
4. Maintainability.
5. Project consistency.
6. Performance.
7. Developer experience.
8. Long-term sustainability.

Personal preference should not be the primary reason for a project-level
decision.

---

# Updates to This Code of Conduct

This Code of Conduct may be updated as the project evolves.

Changes should be documented through normal project governance and should be
communicated clearly to contributors when the changes materially affect
expected behavior.

---

# Acknowledgement

By participating in Tech Monster project spaces, contributors are expected to
follow this Code of Conduct.

Contributors who disagree with a technical decision are still expected to
communicate respectfully.

Constructive disagreement is welcome.

Disrespectful behavior is not.

---

# Final Principle

Tech Monster should be a place where developers can:

- Build software.
- Learn from each other.
- Ask questions.
- Challenge technical decisions.
- Improve code.
- Share knowledge.
- Contribute safely.
- Grow as engineers.

Treat people with respect, review code fairly, protect sensitive information,
and keep technical discussions focused on building a better project.

Thank you for contributing to Tech Monster.
